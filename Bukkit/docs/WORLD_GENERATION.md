# 世界生成系统 - Level1

> ## ⚠️ 最重要的坑：`ChunkData.setRegion` 的 max 参数是「排他」的
>
> Bukkit/Paper 的 `ChunkData.setRegion(xMin, yMin, zMin, xMax, yMax, zMax, material)`
> 里，**`xMax` / `yMax` / `zMax` 都是 exclusive**（写到 max-1 为止）。API javadoc 原文：
>
> ```
> @param xMax maximum x location (exclusive) in the chunk to set
> @param yMax maximum y location (exclusive) in the chunk to set
> @param zMax maximum z location (exclusive) in the chunk to set
> ```
>
> 所以「填满一层」必须写成 `setRegion(0, y, 0, 16, y + 1, 16, material)`。
>
> **历史事故**：`fillLayer` 曾经写成 `setRegion(0, y, 0, 15, y, 15, material)`，
> y 区间成了 `[y, y)` 空区间，整个调用被服务端**静默忽略**（不写方块、不报错）。
> 结果所有用 `fillLayer` 铺的层（-16 基岩、封顶磨制凝灰岩、淡灰色混凝土粉末、砂岩、白色陶瓦…）
> 全部消失，只剩各生成器用 `setBlock` 逐块写的内容（例如深板岩混合层），
> 表现为「部分区块只剩底部深板岩混合层、上面全空，后台无任何报错」。
>
> 之所以长期没被发现：`WorldGenDemo.DemoChunkData.setRegion` 当初按**包含**语义实现
> （`..xMax`），于是 `/ctt worldgen ...` 的 demo 看起来完全正常，把真世界的问题掩盖了。
> 现在 demo 的实现也已改为排他语义，与 Bukkit 契约一致。

## 文件结构

### 核心文件

#### 1. ChunkGen.kt - 基础接口
**位置**: `src/main/kotlin/io/github/zzzyyylllty/chotentech/worldgeneration/ChunkGen.kt`

**功能**:
- 定义区块生成的基础接口
- 提供通用工具方法:
  - `randomBlock(vararg blocks)` - 随机选择方块
  - `weightedRandom(materials, weights)` - 按权重随机选择材质
- 扩展函数:
  - `ChunkData.fillLayer(y, material)` - 填充整层
  - `ChunkData.setBlockIfEmpty(x, y, z, material)` - 仅在空气位置设置方块

---

#### 2. Level1Generator.kt - 世界生成器
**位置**: `src/main/kotlin/io/github/zzzyyylllty/chotentech/worldgeneration/Level1Generator.kt`

**功能**:
Level1 的主世界生成器：直接把生成工作交给 `GL1Terrain`，由它判定区域并落块。

**主要逻辑**:
- 创建 `GL1Terrain` 实例，传入区块坐标和世界种子
- 调用 `generate(chunkData)`

> ⚠️ **生成器实例必须是局部变量。**
> `ChunkGenerator` 实例由整个服务端共享，而区块生成是多线程的。
> 如果把 `GL1Terrain` 存进类字段（如 `private var terrainGenerator`），
> 相邻区块并发生成时该字段会被其他线程覆盖，导致一整批区块使用别人的
> 区块坐标 → 用错区域类型（该是 `WALLS` 的区块被当成 `AQYILA` 生成，
> 于是「墙不见了」、区块顶部出现空洞）。

> 历史记录：曾经把主生成改成「只写 y=0 基岩占位 + `submit` 后置生成」两段式，
> 现已回退为直接生成，改为用调试探针定位问题（见 [L1GenDebug]）。

### 地形生成器

#### 3. GL1Terrain.kt - 地形区域调度器
**位置**: `src/main/kotlin/io/github/zzzyyylllty/chotentech/worldgeneration/l1/GL1Terrain.kt`

**功能**:
不再自行铺设地表，而是先判定当前区块属于哪一种**区域（RegionType）**，
再把生成工作交给该区域对应的走廊生成器。

**布局算法**:
移植自 `tinf/1terrain.kt`：在一个 20×20 的区块网格内按固定顺序随机放置各类区域，
最后把剩余空格兜底为 `WALLS`。

世界按 20 区块切分为若干「元区块」，每个元区块用 `(worldSeed, megaX, megaZ)`
派生独立随机种子并独立布局，因此地形可无限延伸，且对同一世界种子完全确定性。
同一个区块坐标永远得到同一个区域类型。

**区域类型 → 生成器 索引表**:

| RegionType | 生成器 | 说明 |
| --- | --- | --- |
| `UNBREAKABLE` | `GL1PlainUnbreakable` | 石头/深板岩混合 + 每格 30% 基岩（挖不通） |
| `WALLS` | `GL1PlainWalls` | 石头/深板岩混合（见第 8 节） |
| `CORRIDORS` | `GL1PlainCorridor` | |
| `AQYILA` | `GL1PlainAquila` | |
| `GILD` | `GL1PlainGild` | |
| `GOTHIC` | `GL1PlainGothic` | |
| `OUROBOROS` | `GL1PlainOuroboros` | |
| `GARDEN` | `GL1PlainGarden` | 丛林花园（群系 JUNGLE，见 10.5 节） |
| `FABLED` | `GL1PlainFabled` | |

**generate 流程**:
1. `RegionLayout.typeAt(...)` 判定区域类型
2. `guard(region, "region-generator")` 执行该区域生成器 —— 异常会带**完整堆栈**进日志
3. `L1GenDebug.report(...)` 回读 `ChunkData` 内容并打印剖面（见第 3.5 节）
4. 若 `SEAL_FILL` 为 true，执行封顶兜底 `sealChunk`

**主要成员**:
- `generate(chunkData)` - 判定区域 → 委派生成器 → 调试回读 →（可选）封顶兜底
- `createGenerator(region)` - 区域类型到生成器的索引表
- `guard(region, step) { }` - 分阶段 try/catch，把失败阶段和堆栈打进日志
- `sealChunk(chunkData)` - 封顶兜底（默认关闭，见下）
- `RegionType` - 区域类型枚举（含调试用 `symbol`）
- `RegionLayout.typeAt(worldSeed, chunkX, chunkZ)` - 查询区块所属区域
- `RegionLayout.layoutFor(worldSeed, megaX, megaZ)` - 取得（带缓存的）布局表
- `RegionLayout.preview(worldSeed, megaX, megaZ)` - 输出符号布局预览，便于校对算法
- `GL1Terrain.regionTypeAt(chunkX, chunkZ, worldSeed)` - 外部查询入口

**放置顺序里有一趟特殊的「大花园段」**（`placeBigGardens()`，见 10.5 节）：
它是**第一趟**，趁网格还全空时先占一块 4×4（最大 8×8）的完整地块 —— 放到后面会被别的区域切碎、
根本凑不出 4×4。概率很低（每个元区块 8% → 3%），其余花园走 `placeGardenScan(1.6)`（2×2，期望 1.6 片）。

**`SEAL_FILL`（默认 false）**:

定位「部分区块只剩底部深板岩层」问题期间先关闭封顶填充：只由调试探针报告，不做任何填充，
避免把「生成器少写了内容」这件事掩盖掉。问题定位完把它改回 `true` 即可恢复兜底。

#### 3.5 L1GenDebug.kt - 生成链路调试探针
**位置**: `src/main/kotlin/io/github/zzzyyylllty/chotentech/worldgeneration/l1/L1GenDebug.kt`

**功能**:
把「某个区块到底断在哪一环」变成可直接读的日志。每生成一个区块，都会**回读
`ChunkData` 自己的内容**，打出一条竖向剖面 `y15 .. y-16`：

- `#` 采样列全有方块（完整层：地坪 / 天花板）
- `-` 部分采样列有（稀疏结构：柱子 / 家具 / 侧墙）
- `.` 采样列全空

于是可以区分三种断点：

| 现象 | 判定 |
| --- | --- |
| 回读剖面完整，但世界里看不到 | 断在「写入之后」的提交 / 保存环节 |
| 回读剖面就是残缺的 | 写入在生成期 `ChunkData` 里就没落地 |
| 参考剖面同样残缺 | 生成器自己中途返回 / 抛异常（看 `guard` 的堆栈） |

**异常区块的详细报告**会额外用内存缓冲（`WorldGenDemo.DemoChunkData`）把**同一个区域生成器**
再跑一遍作为参考剖面 —— 同一生成器 + 不同 `ChunkData`，差异就是答案。报告内容：

```
⚠ 区块 (cx, cz) 区域 WALLS 剖面异常：回读顶部 y=-5，预期 y=15
   chunkData  = <生成期 ChunkData 的实际实现类>
   高度范围    = minY=-64 maxY=320
   回读剖面    = ....................############
   参考剖面    = ################################
   判定        = 生成器本身能写满（参考剖面正常），差异来自生成期 ChunkData → 写入没有落地
```

**日志量控制**:
- 正常区块：只打前 `MAX_NORMAL_LOGS`（20）条，可用 `L1GenDebug.verbose = false` 关掉
- 异常区块：每条都打，上限 `MAX_ANOMALY_LOGS`（200）条
- 每 `SUMMARY_EVERY`（200）个区块打一条累计统计
- 没有服务器实例（离线工具 / 单元测试）时退化为标准输出，方便离线核对


**封顶兜底（sealChunk，当前默认关闭）**:

各区域生成器的可活动高度并不一致（Fabled y5、Corridor y6、Ouroboros y7、Gothic y8、
Aquila y9、Gild y12）。只要某个生成器漏了「结构最高层 +1 → y15 的磨制凝灰岩覆盖」，
该区块顶部就会露出空洞。

`sealChunk` 在生成器跑完后统一兜底：

1. 补齐 `y=-16` 与 `y=16` 的基岩层；
2. 扫描本区块已有的最高方块，把它以上到 `y=15` 全部填成磨制凝灰岩。

由于只写在「已有最高方块之上」，不会覆盖任何生成器已放置的内容，
新增区域生成器也不会再把世界顶部开洞。

> 当前 `SEAL_FILL = false`，即**只报告不填充**：正在定位「部分区块只剩底部深板岩层」
> 的问题，填充会把这个现象掩盖掉。定位完把 `SEAL_FILL` 改回 `true` 即可恢复。

### 走廊生成器

> **区域尺寸已整体放大约 2 倍（容器化）。**
> 各生成器 `regionSizes` 里的尺寸现在表示「滚到的原始尺寸」，实际使用的是它的 **2 倍**作为
> **容器**（=「一个地形」，外圈砌墙），容器内部再用**原始尺寸的子区域尽量铺满**，
> 子区域边界同样砌墙并留门洞。详见 4.8 `SubRegionLayout`。
> 例：Ouroboros 原 2×2/2×3/2×4 → 容器 4×4/4×6/4×8，容器内仍用 2×2/2×3/2×4 铺满。
> Aquila、Gothic、Gild 同理，超级块也同步 ×2。
> （`GL1PlainFabled` 的 `regionSizes` 本来就没被使用、`RoomCorridor` 不在调度表里，两者未改动。）

#### 4. PlainCorridor.kt - 迷宫式走廊生成器（含走廊预设）
**位置**: `src/main/kotlin/io/github/zzzyyylllty/chotentech/worldgeneration/l1/corridors/PlainCorridor.kt`

**功能**:
生成带墙壁和天花板的地下走廊。**连通方向不再固定**，由 `CorridorMaze` 决定
（参考 `tinf/1corridors.kt`）：每个区块上下左右四个边各有一圈墙，
只有「开」的那一侧在墙中间留出通道，因此走廊可以直行、拐弯、丁字、十字、尽头。

**层级结构**:
```
y = 20:       基岩（顶层，见「通用规则」）
y = 16 ~ 19:  深板岩 / 深板岩砖 / 黑曜石 / 强化深板岩
y = 8 ~ 15:   磨制凝灰岩覆盖
y = 7:        海晶灯 / 荧石（灯层）
y = 6:        闪长岩（天花板），中间 2x2 灰色染色玻璃
y = 1 ~ 5:    墙体（白色混凝土 + 磨制闪长岩底）
y = -1 ~ 0:   石头/安山岩/砂砾混合（地板）
y = -11 ~ -2: 深板岩混合层
y = -12:      基岩（底层）
```

**三种形态（按开口数，与 1corridors 一致）**:

| 类型 | 条件 | 表现 |
| --- | --- | --- |
| `CORRIDOR` | 开口 >= 2 | 一般走廊，**内部 4 格宽**（`corridorThickness = 6`），通道也是 **4 格**（`corridorGap = 4`，和内部对齐） |
| `ROOM` | 开口 >= 2 且抽中 15% | 房间，内部 12×12（`roomThickness = 2`），通道 **4 格**，有灯柱和中央矮台 |
| `CLOSED_ROOM` | 开口 == 1 | 尽端小间（内部 4 格宽），放一盏灯 + 箱子/木桶 |

> 通道宽度**统一 4 格**（`corridorGap = roomGap = 4`）：以前走廊开口是 3 格、比 4 格宽的内部还窄，
> 走起来会在每个区块接缝处收一下。测量：942 个走廊区块里，CORRIDOR 931 / ROOM 142 / CLOSED_ROOM 133 个开口**全是 4 格**。

**走廊预设**（`CorridorPreset`，按**区块中心**的平滑噪声 `presetAt` 选，所以同一片区域大多是同一种）:

| 预设 | 实测占比 | 墙 / 地 |
| --- | --- | --- |
| `NORMAL` | ~51%（最多） | 干净的白色混凝土 + 磨制闪长岩底，**不掺任何杂色**，只有普通家具 |
| `OVERGROWN` | ~15% | 藤蔓斑驳：苔藓、苔藓毯、藤蔓、地毯 + 轻微斑驳墙（掺 ~14%） |
| `TERRACOTTA` | ~15% | **底色仍是普通那道墙/地面**，只有噪声补丁（约 28%）换成陶瓦，补丁里摆碎陶瓦/陶罐 |
| `STONE` | ~10% | 同上，补丁（~27%）换成石头 / 圆石 / 安山岩 / 砂砾，补丁里是圆石半砖与小石堆 |
| `DIRT` | ~5% | 同上，补丁（~22%）被泥土 / 草方块盖住，那几片上面才长草，另有根土 |
| `STONE_BRICKS` | ~5% | 同上，补丁（~26%）换成石砖 / 裂石砖 / 苔石砖，补丁里散石砖半砖 |

> **主题预设只做「小修小改」**：底色永远是普通走廊那道墙（y1 磨制闪长岩、y2~5 白色混凝土）
> 和普通石头地面，风格材质只出现在**平滑噪声画出来的补丁**里
> （两层噪声叠加，主层 9 格、次层 27 格，阈值 `PATCH_CHANCE = 38`）——
> 所以是一小片一小片圆滑地铺开，不是一格一格的 3×3 方块。
> 之前是整面墙 / 整个地板都换成风格材质，那太离谱了。
>
> 实测（墙带里真正是墙的格子）：
>
> | 预设 | 底色 | 风格材质 | 补丁平均大小 | 最大一片 | 补丁「内部格」占比 |
> | --- | --- | --- | --- | --- | --- |
> | `TERRACOTTA` | 72% | 28% | 23.5 格 | 189 格 | 41% |
> | `STONE` | 73% | 27% | 26.1 格 | 197 格 | 43% |
> | `STONE_BRICKS` | 74% | 26% | 24.1 格 | 202 格 | 41% |
> | `DIRT` | 78% | 22% | 11.6 格 | 102 格 | 36% |
>
> （对照：原来是按 3×3 方块整块换，补丁平均只有 9 格、「内部格」占比 ~11% ——
> 一眼就能看出是一个个方块。现在内部格占比 36~43%，也就是成片、圆滑的。）
>
> 补丁里还会加**对应风格的小装饰**：陶瓦段躺几块碎陶瓦和陶罐、石头段是圆石半砖和小石堆、
> 石砖段是石砖半砖、泥土段是根土和草。碎石堆也跟着预设走（陶瓦段掉陶瓦渣、石头段掉碎石）。
> 这些立体装饰**只放在能走的那 4×4 内部**，不会摆进墙带或门洞里把通道堵窄。
> `OVERGROWN` 不受影响，它就是「藤蔓斑驳」那一款，保持原来的轻微杂色（~14%）。

> **预设噪声格点必须远大于 16**（`PRESET_CELL = 120`）：相邻区块中心相距 16 格，
> 若格点只有 10 格，两个采样点会落在不同格点里，风格退化成一片花斑
> （实测「相邻区块同风格」只有 31%，等于纯随机）。120 时实测 ~80%。

**有门 / 洞口的一侧 = 过道**（重要）:

区域交界那一侧原本也是普通墙带：6 格厚的墙里只留门洞，于是能走的只有区块正中的 4×4，
门还常常开在两侧的墙里（门后是墙）。现在改成：

| 侧边情况 | 墙带 |
| --- | --- |
| 普通迷宫开口 | 墙带留出 **4 格宽**的通道（`corridorGap = 4`，正好等于内部宽度，不再出现 3 格窄口） |
| 区域交界 + **无门** | 整条墙带照砌（6 格厚） |
| 区域交界 + **单门 / 双门 / 洞口** | **整条墙带打成过道**，只在贴着交界的那 1 格砌墙（且只有 `doorOwner` 一侧砌），门装在这道墙上 |

所以走廊走到门口时，路是「内部 4×4 → 过道 6 格 → 交界上带门的墙」，而不是把门埋进墙里。
过道里的地板、天花板、两侧的侧墙仍然是正常生成的，家具也只会落在内部（`open` 区间）内。
探针 `PassageProbe` 验证：过道整条可走、门内侧那一格一定走得到、交界线只由一侧砌墙（无缺口 / 无叠墙）。

**破败装饰**（全部确定性，同一区块每次一致；**只属于 `OVERGROWN` / `DIRT` 预设**）:

| 装饰 | 做法 |
| --- | --- |
| 墙体斑驳 | `wallMaterialFor`：`OVERGROWN` 掺约 14%（圆石/苔石/裂石砖/灰混凝土 + 3% 铁栏杆），`NORMAL` 为 0 |
| 裸露钢筋 | `OVERGROWN` 中约 3% 的墙块换成 **铁栏杆**（仍然挡路，只是能看穿） |
| 苔藓 | `OVERGROWN` 地板约 16% 铺苔藓块，其中一半再加苔藓毯 |
| 藤蔓 | 贴墙、从天花板上往下挂（只填空气，所以放在最后一步） |
| 地毯 | `OVERGROWN` 以 2×2 为单位成片铺（22%），5 种颜色随机 |
| 家具 | 按 3 格粗网格撒：木桶堆、箱子、炼药锅/堆肥桶、灯柱、木板/碎石堆、蛛网、木桶塔。**门洞正对着的那一条内部格不放家具** —— 走廊内部只有 4 格宽，一张 2~3 格长的木板堆贴着墙摆下去正好能把门洞封死（实测封死 3 处 → 0） |

**贴墙装饰**（`generateWallDecor`，**所有预设**都有，2025 新增）:

沿墙按**世界坐标**每 4 格一个装饰位（东西向的墙沿 Z 数、南北向的沿 X 数），
所以相邻区块会连成一条整齐的线，而不是一块一块乱撒。
装饰一律摆进**贴着墙的那一格空气**里；那一侧没有墙（过道墙带是空的、门洞被挖空了）就整个跳过。

| 权重 | 内容 |
| --- | --- |
| 28% | 壁挂火把 `WALL_TORCH`（`DIRT` / `OVERGROWN` 里 1/3 换灵魂火把） |
| 8% | 灵魂火把 `SOUL_WALL_TORCH` |
| 7% | 红石火把 `REDSTONE_WALL_TORCH`（暗红，机房味） |
| 15% | **横向铁链「管线」**：贴着墙在 y4 拉 2~4 格，1/3 概率在起点下面吊一盏灯（墙断了就停） |
| 12% | 吊灯：y5 铁链 + y4 灯笼（`hanging = true`，脏预设换灵魂灯笼） |
| 5% | 天花板铃铛 `BELL`（`attachment = CEILING`，挂在墙边） |
| 9% | 地面贴墙摆件：花盆（花草 / 蕨 / 蘑菇按预设）、蜡烛（1~4 根、直接点亮）、陶罐 |
| 7% | 地面贴墙容器：木桶 / 箱子 / 陷阱箱 / 炼药锅 / 堆肥桶 |
| 9% | 空着（留白） |

> **朝向约定**：`facing` = 方块正面 = **从墙指向房间里**。原版墙上的火把就是这个规矩
> （挂在西边墙上时 `facing = EAST`，火苗朝屋里）—— 实测 686 支火把，背后没有墙的 0 支、
> 朝墙的 0 支。铁链 `axis` 顺着墙（实测 652 节，轴向错 0 节）。

> **有碰撞体积的（花盆 / 容器 / 蜡烛）只放内部空间 `open`**：过道墙带是走道和门口，
> 在那里摆木桶会把通道堵窄、甚至把门口堵死（探针 `PassageProbe` 会报
> `unreachable door sills` / `band cells not walkable`，实测分别从 25 / 192 改回 0）。

> **「墙」用白名单判定**（`WALL_MATERIALS`），不用 `Material.isOccluding()`：
> Paper 的 `isOccluding()` 要查注册表（无头探针跑不了），而且白名单更准 ——
> 铁栏杆、藤蔓、家具都不算墙，火把不会挂到它们身上。

**两种哈希**（很容易踩坑）:
- `hash(x, y, z, salt)`：`x`/`z` 必须传**区块内 0..15 的局部坐标**，内部会换算成世界坐标，
  所以同一个方块在哪个区块里算出来都一样；
- `rawHash(a, b, c, salt)`：不再叠加区块坐标，用于**坐标本身已经是全局量**的场景
  （噪声格点、地毯的 2×2 网格、家具粗网格），否则会跨区块错开。

**可调常量**（都在类顶部集中定义）:
- `corridorThickness = 6` —— 一般走廊墙厚（内部 16-2×6 = 4 格宽）
- `roomThickness = 2` —— 房间墙厚（内部 12 格）
- `corridorGap = 4` / `roomGap = 4` —— 通道宽度（**统一 4 格**）
- `wallBottomY = 1` / `wallTopY = 5` —— 墙高
- `PRESET_CELL = 120` —— 预设噪声格点大小（方块）
- `PATCH_CHANCE = 38` / `PATCH_CELL = 9` —— 主题补丁的阈值与噪声格点（方块）
- `WALL_DECOR_STEP = 4` / `WALL_DECOR_OFFSET = 1` —— 贴墙装饰的间距与相位（沿墙每 4 格一个位）
- `WALL_DECOR_PROBE_Y = 3` —— 探「那一侧是不是墙」的高度（门洞只挖到 y3，所以正好把门洞排除）
- `WALL_DECOR_CHAIN_Y = 4` —— 横向铁链「管线」的高度

**地下混合层也改成位置哈希了**：`fillLayerStoneMixed` / `fillLayerDeepslateMixed` 原来用
`ChunkGen.weightedRandom`（taboolib 的全局随机），同一区块生成两次，y-11~0 那十几层图案每次都不一样
（探针里是 `same chunk twice, diff=1887`）。现在走 `pickWeighted(材质表, 权重, hash(x,y,z,SALT_STONE))`，
**diff = 0**。

**连通性由 `CorridorMaze` 保证**:
- 世界按 16×16 区块的「迷宫块」切分，块内用随机生成树（frontier / Prim）保证全连通；
- 跨迷宫块的边界用**全局边界 key** 决定开口，交界两侧算出来必然一致；
  每条边界段再强制开一个口，保证迷宫块之间一定连通。

#### 4.5 CorridorMaze.kt - 走廊连通性模型
**位置**: `src/main/kotlin/io/github/zzzyyylllty/chotentech/worldgeneration/l1/corridors/CorridorMaze.kt`

**功能**:
移植 `tinf/1corridors.kt` 的迷宫思路：给定 `(worldSeed, 区块坐标)` 返回该区块的
开口位掩码（`UP` / `DOWN` / `LEFT` / `RIGHT`）与区块类型。

**要点**:
- 「父格 → 子格」的方向位，父格记该方向、子格记**相反**方向（写反会导致开口对不上、迷宫断连）；
- 边界开口一律取坐标较大的一侧做 key，保证交界两侧一致；
- 生成树 + 强制边界开口 ⟹ 无限世界整体连通、无密封区块；
- **每个格子至少有一条通向「非实心区域」的开口**：`RegionLayout` 里 `WALLS` / `UNBREAKABLE` 是实心填充，
  开口朝着它们等于没有出口，该格子就成了进不去的密闭房间。这种格子会被改开一条朝向非实心邻居的边
  （两侧同时改，只在迷宫块内部），所以「走廊被封闭」的情况从约 3% 降到 0.07%。

**验证结论**（离线探针，4×4 迷宫块 / 4096 区块）:
- 邻居开口不一致：0
- 无开口的密封区块：0
- 16/16 迷宫块各自全连通；类型分布约 CORRIDOR 66% / CLOSED_ROOM 22% / ROOM 11%
- 走廊区块「四面全封」：3.14% → **0.07%**（残留的是极少数迷宫块边界格子，见上）

#### 4.6 RegionGateway.kt - 区域交界的门与洞口
**位置**: `src/main/kotlin/io/github/zzzyyylllty/chotentech/worldgeneration/l1/RegionGateway.kt`

**功能**:
**只做规划与装门，不再自己去挖方块。** 两个不同 `RegionType` 相邻时，本类算出这一侧
交界处应该留什么通道；区域生成器在砌自己那道交界墙时调用 `opensAt(...)` 把这些格子
**跳过**（门洞自然就在墙里留出来了），再由其中一侧调用 `placeDoors(...)` 装上唯一的一层门。

| 形态 | 概率 | 说明 |
| --- | --- | --- |
| 无门 | 40% | 整道墙封死 |
| 单门 | 25% | 中间一扇木门 |
| 双门 | 20% | 中间两扇镜像对开木门 |
| 洞口 | 15% | **4 宽** 3 高、无门的洞口（走廊内部也是 4 格，正好对齐） |

> 与 `WALLS` / `UNBREAKABLE` 相邻时一律「无门」（门后是实心方块，没意义）。

> **开孔位置必须落在过道里**（`DOOR_ZONE_MIN..DOOR_ZONE_MAX` = 6..9）：
> 原来沿轴位置取 5..10，而 `GL1PlainCorridor` 的一般走廊内部只有 4 格宽（6..9），
> 于是约 1/3 的门开在走廊两侧的墙里 —— 门后面还是墙，根本走不过去。
> 现在收窄到 6..9（单门 6..9、双门 6..8、洞口 7..8），其他生成器的内部通道都更宽，收窄对它们无影响。

> **门材质**：每道门有 `IRON_DOOR_CHANCE`（5%）概率是**铁门**，其余是木门。
> 材质同样由共享 key 决定，所以交界两侧一定一致；双开门两扇共用方案里的同一个值，
> **要么都是木门、要么都是铁门**，不会出现一扇木一扇铁。
>
> ⚠️ 铁门不能用手开，只能靠红石（按钮 / 拉杆）—— 也就是这些通道默认是「锁住」的。
> 想改成自动带按钮、或者干脆把铁门换成别的材质，改 `RegionGateway` 顶部常量即可。

**交界线的密封由「装门的那一侧」单独负责**（重要）:

`RegionGateway` 只给方案，真正砌墙的是生成器。走廊这类生成器在**有门 / 洞口的一侧**会把整条墙带
打成过道（见 4 节），所以它在这一侧只砌**贴着交界的那 1 格厚的墙**，而且只有 `doorOwner` 那一侧砌：

```
   走廊块(非 owner)          对面块(owner)              世界坐标
   ┌──────────────┐        ┌──────────────┐
   │ 内部 4×4     │        │ 内部 4×4     │
   │ 过道(空)     │        │ 过道(空)     │
   │ 全空 ────────┼────────┼── 1 格厚墙 + 门 ──┤   ← 交界线
   └──────────────┘        └──────────────┘
```

两侧都砌就会叠出两层墙 / 两层门，两侧都不砌就会漏 —— 探针 `PassageProbe` 专门验证了
「owner 侧没有多余缺口」「非 owner 侧没有多余墙」「非 owner 的对面确实砌了墙」三项都为 0。

**为什么改成「生成器自己留门洞」**（修掉的三个问题）:

原先的做法是交界墙照砌、再由本类从边缘往里挖。带来三个 bug：

| 问题 | 原因 | 现在 |
| --- | --- | --- |
| **两层门** | 交界两侧都装了门 | 只有**坐标较大的一侧**装门（`doorOwner`），另一侧只留空 |
| **挖坏旁边房间** | 挖的时候不知道墙有多厚，只能「一直挖到空气」，会穿过生成器内部的隔墙 | 改成**跳过格子**，一格都不会多挖 |
| **双开门合页挤在中间** | 只按「第几个门」定合页，没考虑门朝向 | 按**门朝向 + 沿轴低端**推合页，两扇必然镜像（探针已验证） |

**两侧一致**:
- 边界 key 取坐标较大的一侧（`A 的南边` 与 `B 的北边` 拿到同一个 key），
  形态 / 开孔区间 / 高度两边必然相同，所以门洞一定对穿；
- **走廊的迷宫开口必须能过去**：区域布局很碎（约 93% 的区块贴着区域边界），
  而走廊在区域边界那一侧会压掉自己的迷宫开口、只由本条交界的方案决定。
  所以只要交界**任一侧是走廊区域、且它的迷宫在这条边上开口**，就强制给一个可通行形态
  （只在 单门/双门/洞口 里选，不含「无门」）—— 否则走廊格子可能四面全封。
- **合页方向按实机反馈校准过**：门的 `hinge` 是相对**门自身朝向**定义的（门朝外看时自己的左手边），
  所以「沿轴低端那扇门」的合页是：
  `北墙 → LEFT`、`南墙 → RIGHT`、`西墙 → RIGHT`、`东墙 → LEFT`（这样两扇合页在外、门缝在中间）。
  如果某一侧仍然合页朝内，把该方向加进 `HINGE_FLIP` 即可（只影响双开门）。
- `WALLS` / `UNBREAKABLE` 是实心填充区域，任一侧是它们时**两侧一致地不开门**
  （否则门后就是实心方块，而且不会出现只挖了一半的情况）。

**调用位置**：`GL1Terrain.generate()` 第 3 步，在区域生成器之后、封顶之前。

#### 4.7 RegionBoundary.kt - 区域边界判定（唯一标准）
**位置**: `src/main/kotlin/io/github/zzzyyylllty/chotentech/worldgeneration/l1/RegionBoundary.kt`

**功能**:
回答「这里是不是区域的结尾」，返回四周中「邻居 `RegionType` 与本区块不同」的方向位掩码。

**为什么需要它（修掉的问题）**:
之前每个走廊生成器都用自己的内部区域网格判断边界（Aquila 用 12 区块超级块 + 2×2~6×2、
Gild 用 8 区块 + 2×4~8×4、Gothic 用 12 区块 + 3×3/4×4），而 `GL1Terrain` 用的是
20×20 元区块的 `RegionType` 布局。两套判断互不相干，于是：

- Aquila 认为自己是**内部**区块（不砌墙），隔壁区域的生成器却砌了外墙
  → 在 Aquila 区域里直接「裸露」出别的区域的外墙，而且没有对应的门洞；
- 反过来也会出现区域内部忽然多出一堵只砌了半边的墙。

**现在**：以 `RegionType` 为准。各生成器把「自己的内部区域边界」与
「`RegionBoundary` 判定的区域边界」**取并集**来砌墙（`GL1PlainFabled` 原本完全不砌边界墙，
现在补了一道木板墙）。因为只依赖 `RegionLayout`，交界两侧算出来天然一致，
不会出现只砌一半的情况。

**方向位**（与 `CorridorMaze` 取值一致）：`NORTH=1`、`SOUTH=2`、`WEST=4`、`EAST=8`。

**验证结论**（离线探针，48×48 区块）:
- 邻居两侧不一致：0
- 边界区块占比约 93%（区域布局比较碎，绝大多数区块至少有一侧是区域边界）
- Aquila / Fabled 的边界区块：所有边界侧都砌上了墙

#### 4.8 SubRegionLayout.kt - 容器放大与子区域铺满
**位置**: `src/main/kotlin/io/github/zzzyyylllty/chotentech/worldgeneration/l1/SubRegionLayout.kt`

**规则**:
1. 生成器滚到的尺寸 **×2** 当作**容器**（「一个地形」，外圈砌墙）→ 地形整体大一倍；
2. 容器内部用**原始尺寸**的子区域**尽量铺满**，子区域边界同样砌墙（内墙）→
   一个大区域被分成几个小区域 / 小房间。

| 生成器 | 原始尺寸（子区域） | 容器（×2） | 超级块 |
| --- | --- | --- | --- |
| `GL1PlainAquila` | 2×2 2×4 4×2 2×6 6×2 | 4×4 4×8 8×4 4×12 12×4 | 12 → 24 |
| `GL1PlainGild` | 2×4 4×2 8×4 4×8 | 4×8 8×4 16×8 8×16 | 8 → 16 |
| `GL1PlainGothic` | 3×3 4×4 | 6×6 8×8 | 12 → 24 |
| `GL1PlainOuroboros` | 2×2 2×3 2×4 | 4×4 4×6 4×8 | 12 → 24 |

**铺满算法**（扫描式贪心）: 每个空格按优先级挑尺寸 ——
① 两个方向都能整除剩余空间的（最能铺满）→ ② 能正好收边的 → ③ 最大的两个里随机（保留变化）。

**确定性**: 布局只由 `(worldSeed, 容器原点, 容器尺寸)` 决定并带缓存，区块生成并发也一致。

**子区域之间也要能走通**: 生成器把子区域边界并进「要砌墙的那一侧」判断后，
同样用 [RegionGateway] 的 `planForSubRegion(...)`（区域交界优先，其次子区域）留门洞，
否则放大后的地形会变成一堆密封盒子。

> ⚠️ `planForSubRegion` 必须校验「这一侧确实是该子区域的边」（`chunkX/chunkZ` 落在 `sub` 的边界上），
> 否则子区域**内部**的区块四边都会拿到方案，会在没有墙的地方**凭空装门**。

**验证结论**（离线探针，每个容器 36 个随机原点 × 4 个生成器全部容器组合）:
覆盖 **100%**、子区域尺寸全部取自原始尺寸、结果确定性一致。

#### 10.5 GL1PlainGarden.kt - 丛林花园生成器
**位置**: `src/main/kotlin/io/github/zzzyyylllty/chotentech/worldgeneration/l1/corridors/GL1PlainGarden.kt`

**功能**:
一片开阔的室内花园：草地、草丛、杜鹃花丛、杜鹃树，四周和中间零星分布「跨区块的墙」与 3×3 砂岩柱子，
顶上盖一层浅绿/深绿玻璃，再往上封屏障。对应 `RegionType.GARDEN`。

**花园段尺寸**：生成器本身对尺寸没有任何假设（区域边界全靠 `RegionBoundary` 按区块判定），
2×2、4×4 乃至 8×8 都能正常生成。布局侧的放置见 `RegionLayout`：

| 放置 | 尺寸 | 概率 |
| --- | --- | --- |
| `placeBigGardens()`（**提前**占一块完整的地，见 3 节） | 4×4 起，最大 8×8（越大越罕见） | 每个元区块 3%（原来 8%），其中 4×4 占多数、8×8 约百里挑一 |
| `placeGardenScan(1.6)`（扫描式） | 2×2 | 期望 1.6 片/元区块（原来 4 片 + 密集扩展），**不再做密集扩展** |

> **花园整体概率下调 60%**（`placeGardenScan` 的期望值、大花园概率、`weightedFill` 里的 GARDEN 权重 4 → 2）。
> `placeGardenScan` 接受小数期望值：**开局就把这次放几个抽定**（`toInt()` 个 + 以小数部分为概率再多一个）——
> 放到循环里现抽不行：那时网格已经没多少空地，第二片经常放不下去，概率会掉一大截（实测 1.6 只落到 1.0）。

实测（种子 `-6365964130700865445`，201×201 区块 / 25 个元区块）：GARDEN 区块占 **1.82%**（原来 4.64%，正好 **-60%**），
173 个连通片里 **168 个是 2×2**，还有一片 36 区块（6×6）的大花园，
落在「≥16 区块」大花园里的区块占花园区块的 4.9%。

**树叶**：所有树叶（橡树 / 杜鹃 / 开花杜鹃）都写了 `persistent = true`，**永不凋零** ——
花园里那些「粗藤蔓」树叶周围没有原木，不加这个标记会在区块 tick 之后自己掉光。

**生物群系**：GARDEN 区块的群系是 **JUNGLE**。
> `ChunkGenerator.ChunkData`（paper-api 1.21.4）**只有 `getBiome`、没有 `setBiome`**，生成阶段改不了群系，
> 所以由 `listener/onGardenBiome.kt` 在 `ChunkLoadEvent` 里补一次：只处理 GARDEN 区块，
> 按 4×4 的群系单元写 `World#setBiome(x, z, Biome.JUNGLE)`（一个区块 16 次调用），
> 写完再加载时第一格判断就是 JUNGLE 直接返回；**其它区域的群系一律不动**。

**层级结构**:
```
y = 21:       屏障（封顶）
y = 20:       浅绿玻璃 35% / 深绿玻璃 35% / 空气 30%（玻璃天窗，压在墙顶上）
y = 10 ~ 19:  去皮白桦木（y10 以上全是）
y = 5 ~ 9:    淡灰色混凝土粉末 / 圆石 / 苔藓圆石 + 去皮白桦木
              （白桦概率随高度 20%→88% 上升；y5~7 还有 45% 概率退化成底部那七种）
y = 1 ~ 4:    砂岩 / 平滑砂岩 / 白桦木板 / 绿色混凝土 / 苔藓块 / 圆石 / 苔藓圆石（等权，各 ~14%）
y = 0:        草方块（地板）
y = -1:       石头混合
y = -11 ~ -2: 深板岩混合
y = -12:      基岩            ┐
y = -13 ~ -16: 强化深板岩 / 黑曜石 / 深板岩砖 / 深板岩（从下到上）  ┘ 通用底层，见「通用规则」
```
（墙高 20：y1~y19 是墙体本体，y20 是压在墙顶上的玻璃层。
**花园不铺通用顶层**——那四层 + y20 基岩会盖掉它的天窗。）

**结构**:

| 结构 | 规则 |
| --- | --- |
| 区域边界墙 | **只有邻居是「别的区域」时才砌**（`planFor` 只在邻居区域类型不同时给方案）：花园挨着花园的那一侧是敞开的，花园之间完全连通；门洞由 `RegionGateway` 留空 + 装门（只有一侧装） |
| 跨区块的墙 | 按「区块 = 一格」的网格撒，墙线落在**两个区块中间**那条线上（局部 x=8 / z=8，即世界坐标 x ≡ 8 (mod 32)），**不落在区块边界上**；一条线以 32 格（2 个区块）为一段、40% 概率决定，相邻区块拼起来就是跨区块的连续长墙且接缝一致。**材质是纯平滑砂岩**（这是「一般墙壁」，不是区域边界墙，用分层做旧那套会和踢脚线搭不上） |
| 墙线的门洞避让 | **只对墙线真正撞上区域墙的那一格生效**（i==0 查北/西方案、i==15 查南/东方案）。早先写成「整条线都拿 fixed 去查门洞」，于是只要两端任一侧有门，整条墙线的 y1~y2 全被跳过 —— 墙像浮在半空、踢脚线也跟着断（这次就是它） |
| 3×3 柱子 | 每格按哈希决定放不放、放哪（x/z ∈ 4..11）、用哪套配方（5 种：切制砂岩塔 / 平滑砂岩方柱 / 苔石遗迹柱 / 白桦木柱 / 高砂岩柱），配方里用到砂岩、砂岩墙、砂岩楼梯与台阶做塔尖 |
| 区块内容 | 30% 只出墙、25% 只出柱子、15% 两者都有、30% 什么都不出（纯草地） |
| 踢脚线 | 贴着墙 / 柱子的一格 y1 是 `SMOOTH_SANDSTONE_STAIRS`，**完整的那一面朝墙**（楼梯的 `facing` 就是高的那一面，所以 `facing` 指向墙）；柱子和墙的**四个拐角**也会补一格，并且**显式设置楼梯 `shape`**（只给 `facing` 的话默认 `STRAIGHT`，拐角处接不上）：左右哪一侧是墙（或另一条踢脚线）就把内角补在那一侧（`INNER_LEFT` / `INNER_RIGHT`），直墙那一条保持 `STRAIGHT`；**门洞正前方那一格不放**，免得门口卡一级楼梯 |
| 墙线自由端收口 | 跨区块墙线在区块边上的那一头，踢脚线要能**拐过去包住墙头**（不然就平着断在那里）。`wallAt()` 对区块外的格子会解析地算两类墙：`lineWallAt(wx,wz)`（跨区块墙线）和 `neighbourRegionWall(wx,wz)`（邻区块的区域边界墙）—— 和砌墙用同一套判定，所以跨区块必然对得上（实测收口拐角 51 处，改前 0） |
| 踢脚线的完整覆盖 | 探针会扫**所有**「y1 是空气、且八邻里有墙」的格子（门洞本身与门洞正前方除外），检查是否都有踢脚线：实测 **0 处漏** |
| 踢脚线正上方留空 | 踢脚线那一格 y2 **不放任何东西**（藤蔓、树叶都会跳过）—— 楼梯顶上压着方块看着就是「状态不对」。y3 以上照常挂藤蔓 |
| 门洞避让 | 门洞本身那几格（墙被挖掉的 y1~y3）不放任何装饰——不放踢脚线、不放藤蔓树叶、不长草 |
| 藤蔓 / 树叶 | 贴区域墙内侧那一格从 y2 往上：33% 藤蔓（贴墙那一面 set 上）、21% 橡树树叶；墙被门洞挖掉的那几层不挂（否则会悬空）。墙 / 柱子周围另有 18% 概率挂橡树树叶当粗藤蔓。**树叶全部 `persistent = true`（永不凋零）** |
| 地面 | 草方块上**几乎铺满**：草 46% / 高草丛 40% / 蕨 5% / 杜鹃花丛 4%，只剩 5% 空着（实测可铺地面覆盖率 **94.2%**）；每格 30% 概率一棵杜鹃树（橡木树干 + 杜鹃树叶，只填空气、整棵保证在区块内） |

> **高草丛是两格高的**（`Bisected`）：只放一个 `TALL_GRASS` 的话游戏里只会出现下半截，
> 上半截要另外放一个 `half = TOP` 的方块。统一走 `ChunkGen.setDoublePlant()`（走廊的泥土预设同样用它）。
> 实测 7632 丛高草，**缺上半截 0**。

| 非花园邻居那一侧有墙 | 全部有（真正的区域边界才砌） |
| 区块内容 | 中间墙线 73 / 柱子 86 / 什么都没有 152 |
| 同区块两次生成差异 | 0 |

柱子那一圈的实测形状（`y=1`，`S` 直踢脚线、`<` `INNER_LEFT`、`>` `INNER_RIGHT`、`#` 柱子）：

```
z=10   > S S S <      ← 北边一排，两端各补一个方向相反的内角
z=11   S # # # S
z=12   S # # # S
z=13   S # # # S
z=14   S S S S S      ← 南边一排（接上南墙那条踢脚线）
```

对角线上下来的两个角是**镜像**的（西侧 `INNER_RIGHT`、东侧 `INNER_LEFT`），
这样每个角的内角块正好同时顶住相邻的那两条踢脚线。

## 通用规则

### 世界底 / 顶（所有生成器统一，`ChunkGen.fillWorldFloor()` / `fillWorldRoof()`）
底层与顶层的基岩**各自上移 4 格**（原来在 y=-16 / y=16），腾出来的四格从下到上都是
**深板岩、深板岩砖、黑曜石、强化深板岩**：

```
y = 20       基岩（顶层，原来是 y16）
y = 19       强化深板岩
y = 18       黑曜石
y = 17       深板岩砖
y = 16       深板岩
   ...       各生成器自己的结构（磨制凝灰岩一直填到 y15）
y = -4 ~ 15  各生成器的地层（原来是 -15 开始，现在从 -11 开始）
y = -12      基岩（底层，原来是 y-16）
y = -13      强化深板岩
y = -14      黑曜石
y = -15      深板岩砖
y = -16      深板岩
```

| 常量 | 值 | 说明 |
| --- | --- | --- |
| `WORLD_FLOOR_DECOR_Y` | -16 | 底层装饰最下面一格 |
| `WORLD_FLOOR_BEDROCK_Y` | -12 | 底层基岩 |
| `WORLD_FLOOR_MIX_Y` | -11 | 各生成器的地层混合层现在从这里开始 |
| `WORLD_ROOF_DECOR_Y` | 16 | 顶层装饰最下面一格 |
| `WORLD_ROOF_BEDROCK_Y` | 20 | 顶层基岩 |

> **GARDEN 例外**：花园不铺顶层（那四层 + 基岩会把它的天窗盖掉），它自己用
> y20 玻璃 + y21 屏障封顶；底层照常铺。
> 各生成器小节里的地层图是**结构示意**，底/顶两层一律以本节为准。

### y16层
- 所有走廊生成器在 y=20 层生成基岩（原来是 y=16，见上）

### 磨制凝灰岩覆盖
- 对于 y 不满16的结构部分，由磨制凝灰岩覆盖
- 覆盖范围：结构最高层+1 到 y=15
